## 第一部分：击杀音效丢失修复方案

### 背景

用户反馈"击杀音效有时丢失"。经端到端追踪（GSI 包 → gsi_server 队列 → gsi_handler_kills 门控 → audio_manager 播放策略 → pygame），确认丢失不是随机 bug，而是以下几条确定性路径叠加的结果。一个关键事实：`debounce_delay` / `last_kill_sound_time`（gsi_handler_kills.py:21-22）只写不读，是死配置——时间防抖层面不存在丢音，全部丢失来自状态门控与播放策略。

### 问题 1：爆头声压制普通击杀（主因，优先修）

**现象**：一枪爆头后立刻补一个身体击杀，第二声永久静音。"爆头+补枪"双杀极常见，这是用户感知"有时候丢"的最主要来源。

**机制**：
- 击杀/爆头/死亡共用单通道 ch1（audio_manager.py:118）
- 优先级：普通击杀 100、爆头 110（audio_playback_policy.py）
- 爆头声未播完时来普通击杀请求 → `decide_channel_action` 判 `100 < 110` → **drop**（audio_playback_policy.py:106-127）
- `_play_kill_sound_with_retry` 的回退键全部同优先级，逐个也被 drop——重试机制只能救"加载失败"，救不了"策略 drop"
- drop 前计数已推进（gsi_handler_kills.py:854）、该等级未进 `played_kill_levels` → 同一 round_kills 值不会再触发 → 永久静音

**修复方案（二选一，推荐 A）**：

**方案 A：击杀家族内同优先级互抢**
在 `audio_playback_policy.py` 的 profile `kill_preempt_v1` 中，把"击杀/爆头"归入同一抢占组：组内新请求一律 preempt 旧声（连杀场景本来就是新声切旧声，与现有 A2 行为一致），组外维持原优先级规则（死亡声 40 仍会被击杀压制，不变）。
改动点：
- `decide_channel_action` 增加 `preempt_group` 概念：`active` 与 `incoming` 同组时无条件 `preempt`，不比优先级
- 击杀 100 / 爆头 110 标同组 `"kill_family"`
- 效果：爆头声占道时补枪 → 新击杀声切入播放，永不 drop

**方案 B：击杀通道池**
仿照枪声/切枪的通道池（ch0/9/10、ch3/11/12），给击杀分 2-3 条通道轮询。缺点：两声击杀音重叠可能浑浊，且要重新划分 16 通道预算。

**风险**：方案 A 改变"爆头声被后续普通击杀切断"这一点——但用户预期本来就是"每一杀都要响"，切断优于静音。方案 A 改动小、行为可预期，推荐。

**验证**：给 `decide_channel_action` 补单测：`active=headshot(110,busy)` + `incoming=kill(100)` → 期望 `preempt` 而非 `drop`。补集成测试：两次快速击杀（第一爆头）→ 两次 `play_sound` 都真正走策略层（现有测试的 dummy `play_sound` 恒 True，绕过了策略，需改造）。

### 问题 2：回合闩锁卡死一整回合

**现象**：中途加入、断线重连回到进行中的回合，或"round_kills=0 复位包"被队列丢弃时，整回合所有击杀静音，下回合才恢复。

**机制**：
- 回合切换时置闩锁 `await_round_kill_reset`（gsi_handler_kills.py:175-178）
- 闩锁**只**靠"观测到 round_kills ≤ 0"解除（gsi_handler_kills.py:753-767）
- 中途加入时本回合 round_kills 已 >0，永远等不到 0；队列满丢包（gsi_server.py:80-88）也可能恰好丢掉 0 包

**修复方案（三重兜底，全部低风险）**：
1. **回合号兜底**：GSI `map.round` 变化时无条件释放闩锁并重置该 steamid 的计数基线（round 变了说明上回合状态已无意义）
2. **超时兜底**：闩锁置位时间戳 >15s 自动释放（一个 freezetime+对枪时间足够观测到 0；15s 还没见到 0 说明 0 包已丢或中途加入）
3. **释放时基线重置**：兜底释放时把 `previous_round_kills[steamid]` 设为当前 round_kills（而不是 0），避免把存量杀数当成新击杀补播一串

**验证**：补单测——(a) 中途加入：首包 round_kills=3、闩锁置位 → 15s 后（mock 时钟）round_kills 4 → 应播等级 4；(b) round 号 5→6 且 round_kills 直接从 2→1（0 包丢失）→ 闩锁释放、等级 1 正常播。

### 问题 3：回合结束补枪强依赖 match_stats

**现象**：phase=over 瞬间的补枪击杀，若玩家 GSI cfg 缺 `match_stats` 组件则必丢。

**机制**：over 阶段放行最终击杀要求 `round_kills` 与 `match_stats.kills` **同时**增长（gsi_handler_kills.py:770-779 + _is_round_end_kill_delta 251-269）；缺 match_stats 时基线缺失直接返回 False。

**修复方案**：
1. `_is_round_end_kill_delta` 降级逻辑：当数据里从未出现过 `match_stats`（连续 N 帧缺失）时，退化为只看 `round_kills` 增长 + 0.5s 内（over 刚发生）的窄窗口，避免把回合结算的计数噪声当击杀
2. 体检页 / 启动自检增加一项：读取游戏内 `gamestate_integration_fanpai.cfg`，检查 `data` 节是否含 `player_match_stats`，缺失则提示一键重写 cfg（cfg 本来就是程序生成的，`ensure_cfg_exists` 已有重写能力）

**验证**：现有测试 test_gsi_audio_handlers.py:222/258 覆盖了有 match_stats 的路径；补"全程无 match_stats 字段 + over 补枪"用例。

### 问题 4（次要，随手修）

| 项 | 位置 | 方案 |
|---|---|---|
| GSI 缺 phase 时新回合 0.8s 内首杀被过渡防抖吞 | gsi_handler_kills.py:782-793 | 防抖窗口从 0.8s 降到 0.3s；且若该帧有 weapons 快照+开火推断（说明是真实击杀而非残留计数）则放行 |
| 合包 1→3 跳过等级 2 音效 | gsi_handler_kills.py:883-896 | 保持现状（设计取舍：合包只播最高连杀），但在文档/帮助面板注明 |
| LRU 驱逐别名会 stop 共享 Sound 截断正在播的声音 | audio_manager.py:249-259, 277-286 | 驱逐时先检查是否有存活别名共享同一 AudioInfo，有则只删键不 stop |
| 队列满静默丢包无可观测性 | gsi_server.py:80-88 | 丢包计数器 + 每分钟汇总日志，纳入诊断信息 |

## 第二部分：音频资源使用流程改造方案

### 现状与痛点（核实结论）

当前"添加一套自定义击杀音效"的真实流程：

```
打开资源目录 → 记住目录范式 → 手动新建风格文件夹
→ 把文件逐个精确改名为 1.mp3 ~ 5.mp3（UI 无任何提示此规则）
→ 回程序手动点"刷新风格列表" → 逐武器下拉选择
```

核心痛点（附代码位置）：

1. **三套不一致的目录范式并存**：风格目录型（kill_sounds）、武器→风格两级型（weapon_kill_sounds 等）、扁平文件即风格型（death）。用户须分别记忆（audio_manager.py:924-1014）
2. **1-5 数字命名规则零引导**：`find_audio_by_stem` 只认纯数字 stem（audio_manager.py:1016-1039），命名为"ak双杀.mp3"直接静默失效
3. **导入向导识别脆弱**：只认"路径含 kill_sounds 等英文分类根名"的结构（audio_import_wizard.py:54-68），网上下载的音效包几乎全部识别失败；失败原因是英文、无正确结构示例（audio_import_wizard_page.py:455）
4. **无风格管理**：所有音效页均无重命名/删除/查看文件/完整性检查入口
5. **试听只播第 1 连杀**（kill_sound_page.py:391-398 硬编码 `-1`），2-5 连杀音无法在 UI 内核对
6. **手动刷新**：往目录放文件后不自动感知（kill_sound_page.py:249,333）
7. **体检不查完整性**：只查目录存在与 config 引用有效，不查风格内 1-5 缺哪个（audio_resource_health.py:47-198），回答不了"为什么不响"

### 改造方案

#### P0：一步式"新建音效风格"向导（消灭手动改名）

在击杀音效/击杀语音/换弹/切枪等页面的工具栏加"➕ 新建风格"：

```
第1步 输入风格名（校验：非空、不与现有风格重名、过滤非法字符）
第2步 选择作用域：全局风格 / 指定武器专属
第3步 拖入或选择音频文件（任意命名、任意数量 1~10 个）
       ↓ 列表按拖入顺序显示，可拖动调整顺序
       每行标注将映射为：1连杀 / 2连杀 / ... / 爆头(可选勾选)
       每行有 ▶ 试听按钮
第4步 点"创建" → 程序复制文件并自动重命名为 1.mp3~5.mp3
       落盘到正确目录 → 自动触发重扫 → 下拉框自动选中新风格
```

实现要点：
- 复用现有 `submit_import_refresh_task` 的重扫链路（audio_import_wizard_page.py:380）
- 复制而非移动源文件；目标已存在时提示覆盖/合并
- death 这类扁平结构在向导内自动适配（用户无感知差异）
- 预估：新增 `dialogs/style_creator_dialog.py` ~300 行 + 各页接入 ~10 行/页

#### P1：导入向导容错升级

识别失败不再是终点，改为进入"手动归类"流程：

```
扫描结果分两栏：✅ 已识别（原逻辑） | ❓ 未识别
未识别栏提供批量操作：
  选中若干文件 → 指定"这是哪类音效"（下拉：击杀音效/击杀语音/枪声/...）
  → 指定风格名（新建或并入现有）→ 按文件名自然排序自动映射 1-5
报错文案全部中文化，附一张"标准目录结构"示意（可折叠）
```

- 改动点：`audio_import_wizard.py` 的 unrecognized 结果结构已带 reason，只需 UI 层加归类交互；reason 翻译表 ~20 行
- 预估：~250 行

#### P1：体检补"完整性检查"

`collect_audio_resource_health` 增加第四类检查 `incomplete_styles`：遍历每个被 config 引用的风格目录，报告 1-5 中缺失的档位与缺失爆头变体。体检页渲染为"风格 X 缺 3、4 连杀音，触发 3/4 连杀时将回退/静音"。
- 预估：core ~40 行 + 页面渲染 ~30 行 + 测试 ~40 行

#### P2：试听档位 + 风格管理

- 每个武器行的"测试"按钮改为分裂按钮：默认播 1 杀，下拉可选 2-5 杀/爆头（kill_sound_page.py:391 处解除硬编码）
- 风格下拉右侧加"⚙"菜单：重命名（目录改名+config 引用同步更新）、删除（移入回收站而非直接删）、在资源管理器中显示
- 预估：~200 行

#### P2：自动刷新

进入音效页时若距上次扫描 >10s 自动重扫（已有 3s TTL 目录缓存，成本低）；保留手动刷新按钮作为兜底。
- 预估：~20 行/页

#### P3（远期）：统一目录范式

把 death 扁平结构迁移为 `death/<风格>/1.mp3` 目录型（加一次性迁移逻辑，保持旧结构只读兼容），三套范式收敛为两套。风险在迁移，收益是扫描/导入/体检代码各删一个特例分支。建议单独排期。

### 实施路线图

| 阶段 | 内容 | 效果 |
|---|---|---|
| 第1批 | 音效丢失三修复（问题1/2/3）+ 问题4 小项 | 用户反馈的"丢音"主病灶解决 |

### 验收标准建议

- 丢音修复：用 gsi_full_sim 回放"爆头+补枪""中途加入""over 补枪（无 match_stats）"三个剧本，音效全响
- 新建向导：一个从未打开过资源目录的新用户，2 分钟内完成一套自定义击杀音效并在游戏内听到
- 体检：删掉某风格的 3.mp3 后体检能明确指出"缺 3 连杀"
