## 一、产品定位（决定所有取舍）

`冷静、专业、轻电竞感、强桌面工具属性`

这是一个**有真实用户在日常使用的桌面工具**，用户在打 CS2 的间隙使用它。因此：

- 「好看」永远排在「好用」和「不出错」后面
- 老用户不该因为一次 UI 更新而找不到原来的功能
- 界面元素在游戏中途被瞥一眼时要能立刻读懂

## 二、硬红线（蓝图明令禁止，不得推翻）

| # | 禁止项 | 为什么 |
|---|---|---|
| R1 | 不重做整套导航结构 | 老用户肌肉记忆 |
| R2 | 不打散现有页面组织关系 | 同上 |
| R3 | 不为了极简把按钮和文案藏起来 | 可发现性 > 简洁 |
| R4 | 不引入复杂视觉特效库 | 打包体积 + 崩溃面 |
| R5 | 不把动画做重 | 工具软件不是展示品 |
| R6 | 不在同一轮 UI 改动里顺手改业务逻辑 | 出事时无法二分定位 |
| R7 | 不在没有测试的情况下批量替换大量页面布局 | 28 个页面无法人工全测 |
| R8 | 不用「好看」为理由破坏高频操作路径 | — |

**风格上明确不走的方向**：炫技型电竞皮肤 / 网页后台风 / 霓虹高饱和配色 / 玻璃拟态 / 发光边框 / 大面积浮夸渐变 / 强动画与频繁动效。

> 若后续有人提"加个毛玻璃/发光/呼吸灯会更现代"——这条已经在 2026-03 被否决过，要推翻必须先改本文件并说明理由。

## 三、必须保留的既有优势（查实，别改坏）

这些是勘察阶段实测确认「已经做对了」的地方。改动时如果发现自己在推翻下面任何一条，先停下来。

### 样式与 token
- **QSS 正文里 `#RRGGBB` 字面量数量为 0**，颜色 100% 来自 `ThemeColors` token（`theme_manager.py`）。全应用只有 45 处 `setStyleSheet`。这是本项目最值钱的架构资产。
- 198 条 QSS 规则、**0 条重复选择器**，没有互相覆盖的历史垃圾。
- `generate_stylesheet` 实测 **0.18ms / 42KB**——**这里不需要加缓存**，加了只是徒增失效逻辑。谁再提"QSS 拼字符串要缓存"，请先看这个数字。
- `ui_design_system.py` 的 `apply_font_scale` 每次从 dataclass 出厂默认值重算（幂等、换档不漂移），字号缩放一处穿透全站。
- `theme_manager.py:530-556` 主动做了「去圣诞树」：正常态 chip 统一中性灰，只让 warn/danger 跳色。**这是克制、专业的状态语言决策，别被"多彩更现代"带偏。**

### 交互与结构
- `PageActionBar` 在 **26/28 页**统一落地（主操作固定底栏 + 左侧反馈文案），是全站最一致的交互语言。
- **切页刻意零动画**，理由写在 `ui_transitions.py:7-9`：不用 `QGraphicsOpacityEffect`，因为它会覆盖卡片的 `QGraphicsDropShadowEffect`。这是正确取舍，别"顺手加个淡入"。
- 骨架屏（页头条 + 3 张灰卡 + shimmer，27 页共享一份）比转圈 spinner 更现代，方向正确。
- 全局滚轮过滤器（`gui_widget.py:1217`）杜绝"滚页面顺手把音量滚掉"——很多同类工具没做的细节。
- `ResponsiveGrid(breakpoints=[(1500,3),(1000,2),(0,1)])` 是真响应式，不是写死列数。
- 正确的尺寸表达范式已存在：`voice_output_page.py:247` 的 `_apply_compact_combo` 用 `setMinimumWidth/setMaximumWidth + QSizePolicy.Expanding`，**这是全站该外推的写法**（而不是 `setFixedWidth`）。

### 稳定性
- 准心 / 闪光 / 屏幕特效的销毁路径写得扎实：join → terminate → kill 三段式、shiboken6 自愈注销、退出分步计时 + 看门狗。
- 音频有 LRU 上限、事件时间线用 `deque(maxlen)`、图标缓存有 500 上限。**不是典型的内存泄漏型项目。**

## 四、打包链路的硬约束（会让"看起来没问题"的优化在发布版炸掉）

> 这是最容易踩的坑：改动在源码运行正常，打包后崩溃或功能消失。

| 约束 | 影响 | 对应规避动作 |
|---|---|---|
| **PyArmor 只混淆根目录 `.py`**（`build_tools/build_release.py:33`） | 把 `config.py` / `gui_widget.py` 拆分到子包，会让这部分代码**失去混淆保护** | 拆巨型文件前必须先确认混淆清单同步更新；否则拆分收益 < 代码泄露风险 |
| **hiddenimports 只扫种子文件一层 AST**（`build_tools/build_release.py:444`） | 任何**懒加载 / 延迟 import / 新增根模块**的优化，都可能只在打包版 `ModuleNotFoundError` | 每次引入新的延迟导入，必须打一次包并冒烟 |
| onedir 安装版与单文件版行为不同 | splash / 资源路径 / 启动时序有差异 | 验收必须在**打包产物**上做，不能只跑源码 |

**推论**：本专项 W3「拆巨型文件」类改造，必须把混淆清单同步作为验收项之一，否则不予通过。

## 六、验收标准（蓝图 §11，本专项补充可量化项）

### 视觉层
- 同类控件样式一致；页面密度均衡；标题/正文/提示/状态层级清晰；第一屏重点明确

### 易用层
- 老用户能快速找到原有功能；页面扫描速度更快；主操作入口更明显

### 稳定层
- 不出现页面无法打开 / 布局错位 / 文本遮挡 / 按钮点不到
- 不影响账号、更新、音频、准心等现有功能
- **打包版本运行正常**（不是源码版）

### 本专项补充：性能层（可量化，见 [01_基线与度量](01_基线与度量.md)）
- 每次启动的卡顿次数、累计停顿时长
- 启动→窗口可见、启动→全就绪
- 退出总耗时
- **"感觉更流畅了"不算验收通过，必须有 `ui_perf_probe.py` 的前后数字。**

---

## 七、改动分级与提交纪律

- UI 改动与功能改动**分开提交**
- 优先级：样式表 → 设计 token → 局部容器 → 页面布局 → 结构重构（越往后越晚做）
- 少改页面内部业务信号和数据流
- 每个阶段结束后重新打包，保留一个可直接打开的发布包 + 源码快照
