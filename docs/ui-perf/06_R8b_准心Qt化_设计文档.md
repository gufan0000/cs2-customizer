### 1-2 「准心已致原生崩溃」——措辞要收紧，但结论站得住

登记册 UP-054 写「已致原生崩溃」。翻到源头（提交 `f51ab0f`，2026-07-14）核对
用户 `native_crash.log`，实际情况是：

- 出事那一帧的**故障线程是主线程**（`main_widget.py` 的 `window.show()` 路径），
  准心线程 `draw_crosshair_loop` 是**并发运行的旁观线程**，不是故障线程本身。
- 提交说明当时写得是准的（「主线程 abort，而准心线程正并发运行 SDL」），
  是**登记册转述时压缩成了「准心已致崩溃」**，把相关性说成了因果性。

**为什么结论仍然成立**：见下一节——准心那条线程做的事本身就违反 Win32 规则，
它是不是那一帧的故障线程，不影响「必须消除」这个判断。
但文案要改成「与原生崩溃强相关且机制可解释」，不是「已证实致崩」。

### 1-3 真正能一锤定音的证据：**准心是主进程里唯一的 SDL 视频窗口**

全仓 `pygame.display` 的使用者只有四个，其中三个都在**子进程**里：

| 模块 | 进程 | 备注 |
|---|---|---|
| `flash_process.py` | 子进程（`multiprocessing`） | 入口显式 `SetProcessDpiAwareness` |
| `kill_icon_player.py` | 子进程 | 同上，父进程一次都不碰 pygame |
| `utility_display.py` | 子进程 | 同上 |
| **`crosshair_animation.py`** | **主进程（与 Qt 同进程）** | **唯一的例外** |

也就是说，「pygame 叠加层放子进程」在这个项目里**早就是既成惯例**，
准心是唯一一个没跟上的。这比任何性能数字都更能说明它该改。

### 1-4 `t_shape` 是够不着的死代码

但全仓 `t_shape` **只有这一处**——UI 的样式单选只给了 `crosshair / dot / circle / custom`
四个，预设包、配置默认值里都没有它。迁移时**不照抄**，处置见 §8。

## 2. 根因：不是「两个图形库抢资源」，是**跨线程操作窗口**

原提交把根因写成「pygame/SDL 与 Qt 在同进程并发抢视频/DPI 资源」。
这个说法的问题是它**指不出正解**——听上去只能靠「别同时用」绕过，
于是就有了今天的兼容模式跳过。

读代码能得到一个更具体、也更可修的机制：

```
主线程（Qt）                          CrosshairDraw 工作线程
  pygame.display.set_mode()  ← 窗口在这里创建，属主线程 = 主线程
                                        pygame.event.get()    → SDL_PumpEvents
                                        pygame.display.flip() → 更新该窗口
```

Win32 的规则：**窗口归创建它的线程所有**，消息队列也归那个线程。
从非属主线程去泵消息、去刷新窗口，会向属主线程投递 input-synchronous 消息。
而主线程此刻若正在做 COM 出栈调用，就得到
`0x8001010d`（`RPC_E_CANTCALLOUT_ININPUTSYNCCALL`）——
**这正是用户 `native_crash.log` 里那一次崩溃记录的异常码。**

> 口径说明：异常码与机制吻合，且该线程确实在并发跑 SDL；
> 但故障线程是主线程，所以这是**机制层面的强关联**，
> 不是「已捕获准心线程崩在某一行」的直接证据。别再把它写成后者。

**这个根因换来的是一条明确的正解**：让窗口的创建、绘制、消息处理落在同一个线程。
Qt 天生强制这一点（QWidget 只能在主线程），所以 Qt 化不是「换个库试试」，
而是**结构性地消灭这一整类 bug**。

## 3. 选型：三条路都摆出来比

| | A · Qt 透明窗（选中） | B · 保留 pygame，绘制搬主线程 | C · pygame 搬子进程 |
|---|---|---|---|
| 消除跨线程操作窗口 | ✅ Qt 强制 | ✅ | ✅ |
| 主进程还有没有 SDL 视频 | ❌ 没了 | ⚠️ 还在 | ❌ 没了 |
| SDL/Qt 的 DPI 认知不一致 | ✅ 结构上消失（只有一套坐标系） | ⚠️ 仍在 | ⚠️ 仍在，但隔离在子进程 |
| 逐像素透明 / 抗锯齿 | ✅ 有 | ❌ 仍是黑色键控 | ❌ 仍是黑色键控 |
| 设置改动的响应链路 | 直接调方法 | 直接调方法 | 要走 IPC |
| 新增常驻进程 | 无 | 无 | **+1**（准心是全程常开，不像闪光/击杀图标是偶发） |
| 与仓库既有实现的关系 | **复用** `EdgeParticleOverlay` 已验证配方 | 无参照 | 与另外三个 SDL 叠加层第 4 次复制 |
| 工作量 | 中（渲染要重写） | 小 | 中 |

**选 A。** 理由不是「Qt 更现代」，而是：

1. **仓库里已经有一个跑在生产的同类实现**（`screen_effect_overlay.py`，1130 行，
   `gui_widget.__init__` 里无条件构造、有独立设置页）。它已经解决了
   透明、置顶、点击穿透、多显示器、按绘制成本自适应帧率这一整套问题。
   R8b 因此不是「设计一套 Qt 叠加层架构」，是**把准心接到已经在跑的那套上**。
2. B 留着 SDL 在主进程，DPI 不一致（用户屏 SDL 见 2560×1440、Qt 见 2560×1368）
   这个已记录的差异原样保留，等于治标。
3. C 与既有惯例最一致，但准心是**全程常开**的，为它常驻一个进程，
   代价与收益不匹配；且会让 SDL 叠加层代码第四次复制。

**C 保留为退路**：若 A 在真实游戏里出现置顶/穿透问题（见 §10 风险 R-2），
C 是已被本仓库验证过三次的备选，不需要重新论证。

## 4. 渲染方案

### 4-1 窗口配方——照抄 `EdgeParticleOverlay`，不要自创

```python
flags = Qt.FramelessWindowHint | Qt.WindowStaysOnTopHint | Qt.Tool
      | Qt.WindowTransparentForInput | Qt.WindowDoesNotAcceptFocus
setAttribute(Qt.WA_TranslucentBackground, True)
setAttribute(Qt.WA_ShowWithoutActivating, True)   # 不抢焦点 = 不打扰前台
setAttribute(Qt.WA_TransparentForMouseEvents, True)
# 再补 Win32 扩展样式：LAYERED | TRANSPARENT | TOOLWINDOW | NOACTIVATE
```

（`screen_effect_overlay.py:314-330` 与 `_apply_windows_click_through()`。
`WindowTransparentForInput` 那两行 `getattr` 兼容写法一并沿用，别简化掉。）

**为什么必须逐项照抄**：这五个属性缺任何一个都会破坏「不打扰前台」这条硬约束——
少 `WA_ShowWithoutActivating` 准心一出现就抢焦点把游戏切出去，
少 `WS_EX_TRANSPARENT` 准心会吃掉屏幕正中的鼠标点击。
这套组合是已经在生产验证过的，不是可以凭直觉重写的样板代码。

### 4-2 一个能真正改善观感的差异：逐像素透明

现在走的是 `LWA_COLORKEY` + 纯黑键控，副作用直接写在代码里：

```python
def dim_color(self, color, factor):
    """下限取1：纯黑(0,0,0)是分层窗口的透明色键，
    深色准心闪烁压暗到精确纯黑会被整块抠成透明（准心出现缺口）"""
```

`WA_TranslucentBackground` 给的是真正的逐像素 alpha：
**这个下限钳制的 hack 可以删掉**，并且准心可以开抗锯齿（斜线、圆圈不再有锯齿）。

⚠️ 但抗锯齿**默认关**，见 §5-3。

### 4-3 尺寸与定位

保持 100×100（§1-1 的既有成果），居中于 `QApplication.primaryScreen()`。

**这是本轮最需要小心的一处**：准心差几个像素就毫无意义。
Qt 的逻辑像素在缩放屏上不等于物理像素，100×100 的逻辑窗口在 125% 屏上是 125×125 物理像素。
落地时必须按 `devicePixelRatio` 处理，并且**几何断言要落在物理像素上**（判据见 §9-2）。
现在的 pygame 版走 `win32api.GetSystemMetrics()` 拿的是物理像素——
换成 Qt 坐标系后如果不显式处理，准心会在缩放屏上偏移。

## 5. 帧率策略

### 5-1 实测：绘制成本根本不是瓶颈

`scripts/probe_r8b_crosshair.py`（离屏光栅化，100×100，每项 400 帧取中位）：

| 样式 | QPainter | QPainter+抗锯齿 | pygame.draw |
|---|---|---|---|
| 十字 | 0.0064ms | 0.0065ms | 0.0028ms |
| 圆圈 | 0.0074ms | 0.0102ms | 0.0016ms |
| 点 | 0.0088ms | 0.0094ms | 0.0019ms |
| 自定义（120 像素点） | 0.0502ms | **0.0652ms** | 0.0475ms |
| 霓虹扩散（3 层环） | 0.0205ms | 0.0287ms | 0.0052ms |

QPainter 比 pygame 慢 1.1~4.6 倍，但两边都在**几十微秒**量级。
最贵一帧 0.0652ms，24FPS 下占主线程 **0.156%**，60FPS 下 0.391%。

**结论：`clock.tick(24)` 的价值不在省 CPU**（省的是 0.1% 级别的东西）。
它真正的作用是限制**合成与唤醒**次数。迁移后保留 24FPS，理由要写成后者，
别再拿「省 CPU」当锁帧的理由——那个说法经不起量。

### 5-2 实测：主线程绘制不制造卡顿

这是比 5-1 更要紧的问题。QWidget 只能在主线程画，也就是和用户拖滑块同一个线程。
UP-079 就是在这里栽的（准心定时器在主线程首次碰 pygame，实测冻结 **426.8ms**）。

`scripts/probe_r8b_mainthread.py`：10ms 心跳探针，每组 6 秒，
样本取**最贵**的组合（自定义像素准心 + 抗锯齿 + 三层扩散环），
窗口设 `WA_DontShowOnScreen`（照常走 paintEvent 与后备存储，永不映射到屏幕）：

| 场景 | 心跳滞后中位 | p95 | 最大 | 画帧中位 |
|---|---|---|---|---|
| 基线（无准心） | 0.000ms | 1.131ms | 11.610ms | — |
| 主线程准心 24FPS | 0.000ms | 1.414ms | **8.289ms** | 0.424ms |
| 主线程准心 60FPS | 0.000ms | 1.310ms | **4.528ms** | 0.374ms |

带准心的最大滞后**比基线还低**——差异完全落在噪声里。
对照 UP-079 那次 426.8ms，**主线程绘制不构成可感知卡顿**。

> 画帧中位 0.424ms 比 §5-1 的 0.065ms 大一个量级，是因为这里含完整的
> `update() → 事件循环 → paintEvent → 后备存储` 链路，不只是光栅化。
> 24FPS 下仍只占主线程 1.0%。

### 5-3 定案

| 状态 | 帧率 | 说明 |
|---|---|---|
| 静态准心（无动画、无击杀联动） | **不跑定时器**（0FPS） | 比现在的 `tick(1)` 更进一步：Qt 只在内容变化时 `update()` 即可，静态准心一帧都不用重画 |
| 空闲动画 / 击杀联动进行中 | **24FPS** | 保住既有成果；理由改写为「限制合成与唤醒」 |
| 抗锯齿 | **默认关，配置可开** | 视觉上更好看，但准心是**功能性**元素不是装饰：抗锯齿会让 1px 细线变成灰边，一部分玩家明确不要。默认保持与现在一致的硬边 |

## 6. 与 GSI 事件的线程模型

击杀事件从 GSI 服务器线程来（`main_widget.py:1220` 注册 `register_kill_handler`）。
Qt 控件只能在主线程碰。

**照抄 `ScreenEffectOverlayManager` 的做法**（`screen_effect_overlay.py:901-928`）：

```
GSI 线程 ──► manager._kill_signal.emit(is_headshot)   # QObject 的 Signal
                    │  (跨线程 → Qt 自动排队投递)
                    ▼
            主线程 _handle_kill()  ──► 置动画状态 + 启动 24FPS 定时器
                    │
                    ▼
            QTimer ──► update() ──► paintEvent()
```

这不是新设计——同一个 GSI 回调**现在就同时喂着**准心和屏幕特效
（`crosshair_animation.register_kill_handler` 里一起注册了两个回调），
屏幕特效那一路已经是 Signal 排队的。R8b 把准心这一路也改成一样。

**要点**：`Signal` 的默认 `AutoConnection` 在跨线程时是队列连接——
不要图省事写成 `DirectConnection`，那等于没改。

## 7. 灰度开关与回退

### 7-1 开关

新增配置 `crosshair_renderer`：

| 值 | 行为 |
|---|---|
| `qt` | 新的 Qt 叠加层 |
| `pygame` | 走现有 `CrosshairAnimationSystem`，**代码原样保留一个发布周期** |

**默认值：`qt`（R8b-E 落地）。**

中途一度定为 `pygame`，理由是「置顶 / 点击穿透 / 缩放屏居中只能在真屏幕上看」。
**那个口径划得太保守了**——这三样绝大部分能程序化验，而且比人眼严：

| 原以为要人眼看 | 实际怎么验的 |
|---|---|
| 「看着像在正中」 | `GetWindowRect` 量物理像素，实测偏差 **0.0px** |
| 「点得动下面的东西」 | `WindowFromPoint` 打屏幕正中，返回的不是准心句柄 |
| 「没抢走焦点」 | `GetForegroundWindow` 三点采样，全程稳定在同一个窗口 |
| 「盖得住游戏」 | 造一个**非置顶**的全屏窗口比 Z 序（准心 Z=28 vs 假游戏 Z=70） |

真正只能靠人眼的只剩**观感**（11 个联动和老版比有没有跑偏），那是主观项，
不构成翻默认值的阻塞——功能正确性已经全部有据。

回退仍是一行：`config.json` 里加 `"crosshair_renderer": "pygame"`，
老实现代码保留一个发布周期。

`CS2C_SAFE_MODE_ACTIVE=1`（兼容模式）下的处置**要改**：
现在是「跳过准心」，Qt 化之后兼容模式**不再需要跳过**——
跳过的理由是 SDL 与 Qt 抢资源，而 Qt 渲染器没有 SDL。
但**本轮不动这一行**：先让两条路并存跑满一个周期，
确认 Qt 路径在真实机器上稳定后，再单独提一次改动去掉兼容模式的跳过。
（这条是本轮唯一一处「明知可以改但故意不改」，理由是回退面要留够。）

### 7-2 回退

- 单个用户遇问题：改 `config.json` 的 `crosshair_renderer=pygame`，零重装。
- 大面积问题：默认值翻回 `pygame`，一行改动。
- 老代码删除时机：**下一个发布周期**，且要先确认没有回退上报。
