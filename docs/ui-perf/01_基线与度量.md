## 一、怎么测

```bash
python scripts/ui_perf_probe.py
```

| 场景 | 命令 |
|---|---|
| 看当前全量基线 | `python scripts/ui_perf_probe.py` |
| 只看最近 5 次启动 | `python scripts/ui_perf_probe.py --last 5` |
| 存快照（每轮开始前做） | `python scripts/ui_perf_probe.py --save docs/ui-perf/baseline_R<N>.json` |
| **与上轮比对（每轮验收必做）** | `python scripts/ui_perf_probe.py --compare docs/ui-perf/baseline_R0.json` |

探针解析的四类日志埋点（口径固定，改埋点必须同步改探针）：

| 埋点 | 产出位置 | 探针正则 |
|---|---|---|
| `[启动相位] X: +Nms (累计 Nms)` | `main_widget.py` | `RE_BOOT_PHASE` |
| `[主窗相位] X: +Nms` | `gui_widget.py` | `RE_WIN_PHASE` |
| `[卡顿] 主线程停顿 Nms (启动后 Ns)` | `core/utils/jank_monitor.py` | `RE_JANK` |
| `退出步骤[X]偏慢: Ns` / `退出清理完成…总耗时 Ns` | `gui_widget.py` 退出链路 | `RE_EXIT_*` |

## 二、R0 基线（2026-08-07 建立，369 次会话 / 88 次有效启动）

快照文件：[`baseline_R0.json`](baseline_R0.json)

### 卡顿分布 —— 本专项的头号靶子

| 项 | R0 值 |
|---|---|
| **每次启动平均卡顿次数** | **4.8 次** |
| **每次启动累计停顿** | **1827ms** |
| 启动期（≤15s）卡顿 | 424 次 |
| 稳态期（>15s）卡顿 | 25 次 |
| **启动期占比** | **94.4%** |

> **结论一：这个软件"稳态使用时几乎不卡"。**
> 449 次卡顿里 424 次（94.4%）发生在启动后 15 秒内。用户抱怨的"微卡顿"，本质是**启动后头 10 秒界面半死不活**，不是用着用着变卡。
> 优化火力应集中在启动期，而不是撒胡椒面式地全局优化。

**每创建一个页面 = 一次 150~640ms 的主线程停顿**，14 个页面排队 → 启动后 2.3s~9.4s 连续卡顿。

代码注释里已经承认了这件事：`单页构建本身要 200-500ms(主线程不可切)`。

## 三、度量缺口（已知不准的地方，修之前别拿这些数字下结论）

| 缺口 | 影响 | 对应问题单 |
|---|---|---|
| **卡顿探测器在 `window.show()` 之后才启动** | 最大的一段停顿（主窗构建 1898~5012ms）**完全测不到**；日志里"启动后 Xs"的基准比进程真实启动晚约 5.3 秒 | 见 [02_问题清单](02_问题清单.md) 度量类 |
| **没有任何内存度量** | "用久了变卡 / 内存增长"这条无法回归 | 同上 |
| 切页只测到"建页"一段 | 用户感知的端到端切页延迟没有埋点 | 同上 |
| 全量测试套件跑不起来 | 625 个用例的回归网形同虚设（实测补一行 conftest 后全量 13.5s 通过） | 同上 |

> **W1 的第一件事就是补齐这几个缺口**，否则后续所有性能改动都没法验收。

## 四、⚠️ 口径版本：R0 的卡顿数字不能和 R1 之后直接比

R1（UP-002）把卡顿探测器从 `window.show()` 之后提前到 `QApplication` 之后，并改用 `_BOOT_T0` 计时。这是**口径变更**，不是性能变化：

| | v1（R0，2.2.1 及更早） | v2（R1，2.2.2 起） |
|---|---|---|
| 探测器启动时机 | `window.show()` 之后 | `QApplication` 之后（单实例守卫后） |
| "启动后 Xs"起点 | 探测器构造时刻 | `_BOOT_T0`（进程真实起点） |
| 主窗构建那 1.9~5.0s 的停顿 | **测不到** | **测得到** |

> **所以 v2 的"每次启动卡顿次数/累计停顿"必然比 v1 大**——那不是劣化，是原先看不见的那段现在看见了。
> 探针已内建守卫：`--compare` 检测到口径版本不同时，对卡顿类指标只并排列数、**不判改善/劣化**。

### 怎么取得 v2 基线（R2 开工前必做一次）

R1 只改了度量设施，未改产品代码行为。**v2 基线必须在装有 R1 埋点的版本实际运行后才能采集**：

```bash
python scripts/ui_perf_probe.py --save docs/ui-perf/baseline_R1.json
```

正常启动软件 2~3 次（含至少一次完整退出）后再跑上面这条命令。得到的快照即 **v2 的唯一起点**，R2 之后都与它比对。

> R1 未生成 `baseline_R1.json`：当时 `%LOCALAPPDATA%` 下已无 v2 会话可采（见 [03_执行日志](03_执行日志.md) R1 条目的踩坑记录），存一份没有有效启动数据的快照只会误导后续比对。
