## 1. 总策略：三场战役，按依赖排序

```
战役一「先可测」 R1            —— 修好尺子。625个测试跑起来 + 卡顿计时对齐 + 内存可测
战役二「再不卡」 R2 → R3       —— 打掉启动期94.4%的卡顿 + 关窗3秒冻结
战役三「后好看好用」R4→R5→R6→R7 —— 显示缺陷 → 页面布局 → 便利性 → 设计系统收敛
长尾   「动结构」 R8a/b/c      —— 受打包约束的结构性改造，最后做
```

排序依据（R0 三结论，不再复述论证）：
1. 卡顿 94.4% 在启动期 → 战役二只打启动期和退出期，不做全局优化；
2. 样式层已被实测排除性能嫌疑 → 战役三是**功能与视觉修复**，不背性能指标；
3. 底子好、规则只落实一半 → 战役三的本质是"铺满已有规则"，不引入新视觉语言。

**轮次 = 会话**：每轮设计为一个工作会话可完成（R8b 除外）。每轮收工执行 README 的"收工四件事"。

## 4. 各轮详细方案

### R1 · 修尺子（战役一，先做，全 S/低）

**为什么第一**：UP-002 不修，卡顿日志时间基准错位 5.3s 且主窗构建那段测不到——R2 的验收数字会是错的；UP-001 修完 625 个用例即恢复（实测 13.5s 全量通过），是 R4/R5/R7 批量改动的安全垫。

|---|---|
| UP-001 | `tests/conftest.py` 增加 offscreen `QCoreApplication` 保障（`QApplication.instance()` 检查 + `QT_QPA_PLATFORM=offscreen`），消除 `test_single_instance.py:22` 的全局崩溃 |

## 6. 全局验证协议

**每轮固定三板斧**：
1. `python -m py_compile <改动文件>` + `python -m pytest tests/ -q`（R1 后全量可跑）
2. `python scripts/ui_perf_probe.py --save docs/ui-perf/baseline_R<N>.json --compare docs/ui-perf/baseline_R<N-1>.json`——任何一项劣化即回滚或在 03 写明豁免理由
3. 蓝图 §10.3 人工回归六页：基础设置 / 账号中心 / 准心设置 / 音乐播放 / 关于软件 / 更新与启动链路

**条件触发**：
- **打包冒烟**（R2/R3/R8 强制）：触发条件 = 动了 import 结构 / 新增模块 / 子进程 / 启动时序。onedir 产物上验证启动、GSI、音频、闪光
- **主题矩阵**（R4/R5/R7）：9 主题 × 2 分辨率 × 2 字号档抽查 + contrast audit
- **GSI 手测**（R2/R3）：真实对局或机器人局，**禁用观战**（观战数据会误触发，见项目记忆）

**提交纪律**：每轮一个分支 `uiperf/R<n>`；每个 UP 项独立 commit；UI 与逻辑改动分开提交（蓝图 §10.1）。

## 8. 明确不做 / 暂缓（防跑偏，与红线互补）
