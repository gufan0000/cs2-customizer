## 2. 每次执行前的任务归一化

开始检查前，先把本次改动压缩成下面这 6 项。

### 2.1 改动主题

示例：

- 帮助文案统一
- `flash` 页基础设置紧凑化
- `voice_output` 页输入与状态联动修复

### 2.2 改动类型

从下面选 1 到 3 个标签：

- 文案
- 单页 UI
- 多页 UI
- 表单交互
- 状态联动
- 配置回写
- 资源路径
- 音频逻辑
- GSI 逻辑
- CFG 逻辑

### 2.3 触达文件

至少列出：

- 改动的页面文件
- 改动的公共组件
- 改动的帮助文案文件
- 改动的测试文件

### 2.4 预估影响页面

按照“直接影响 / 间接影响”列出：

- 直接影响页：本次实际改到的页
- 间接影响页：共享组件、共享样式、共享帮助面板可能波及的页

### 2.5 主要风险

至少写出 1 到 3 条：

- 输入框失去可编辑性
- 帮助说明与真实路径不一致
- 窄宽度出现裁切
- 下拉项丢失
- 配置未写回
- 状态摘要没同步

### 2.6 本次通过标准

至少写清：

- 哪几个页面必须过
- 哪几个测试必须过
- 哪几张截图必须看

## 3. 标准执行流程

## 3.1 第 0 步：静默前提确认

开始前，必须先确认：

- 使用 `offscreen`
- 不会弹前台窗口
- 不会触发真实文件夹打开
- 不会写真实配置
- 不会播真实音频

如果这一步做不到，停止，不进入后续检查。

### 高风险副作用页的额外前置项

凡是涉及以下能力的页面，在静默检查前必须额外断开真实系统写入：

- 写出 `fanpai.cfg`
- 写出运行期 CFG
- 修改 `autoexec.cfg`
- 自动检测并补齐游戏侧配置

当前仓库里的高风险代表页：

- `magnifier_page.py`
- `viewmodel_page.py`
- `hud_color_page.py`
- 以及任何会直接调用 `write_fanpai_cfg`、`setup_autoexec`、`ensure_cfg_exists` 的页面

对这些页面，静默检查前至少满足下面一条：

1. 显式把 `config.csgo_dir` 置空到临时态，避免落到真实 CS2 目录
2. monkeypatch `write_fanpai_cfg`
3. monkeypatch `setup_autoexec`
4. monkeypatch 启动期自动检测或自动写配置逻辑

如果没有完成这一步，就不能进入该页的离屏审图。

## 3.2 第 1 步：静态检查

本步只看结构和一致性，不跑真实交互。

### 必查项

- 帮助 key 是否有映射
- 文案路径是否与代码一致
- 关键配置键是否存在
- 关键下拉枚举值是否存在
- 改动文件是否有明显遗漏的引用点

### 常用动作

- `Select-String`
- `Get-Content`
- 对照已有测试

### 本步输出

- 静态检查通过 / 不通过
- 若不通过，先修再继续

## 3.3 第 2 步：UI 合约检查

本步确认页面骨架成立。

### 每个页面至少检查

- 标题
- lead 文案
- 状态卡
- 帮助按钮
- 关键输入框
- 关键下拉框
- 关键开关 / 单选项
- action bar

### 常用依据

- 页面构造成功
- 关键控件存在
- 默认状态不为空白

## 3.4 第 3 步：交互联动检查

本步确认“不是看着对，而是真的能用”。

### 每个被改页面至少做一组交互

- 输入框输入
- 下拉切换
- 复选框切换
- 滑块变更
- 标签页切换
- 帮助面板展开

### 判断标准

- 配置变化
- 状态条变化
- 摘要变化
- 按钮状态变化
- dependent UI 启用 / 禁用变化

## 3.5 第 4 步：离屏视觉审计

本步只做视觉复核，不做真实前台操作。

### 推荐截图档位

- `1440`
- `1280`
- `980`

### 必看问题

- 裁切
- 横向滚动
- 过窄输入框
- 过长空白
- 按钮遮挡
- 帮助面板展开后挤压
- 文案显示不完整

### 离屏字体风险说明

在部分 `offscreen` 环境里，中文字体可能出现方块或回退渲染异常。

遇到这种情况时，判断原则是：

1. 先看自动化文本断言是否通过
2. 再看布局、间距、遮挡、滚动、按钮位置这些“结构性问题”
3. 不要仅凭离屏截图中文字变方块，就直接判定为软件文案显示 bug

只有当“文本断言失败”或“页面结构也异常”同时出现时，才按真实问题处理。

## 3.6 第 5 步：专项测试

按改动类型补跑对应测试。

### 典型映射

- 帮助文案：`test_ui_help_panel_texts.py`
- 交互控件：`test_ui_form_and_help_interactions.py`
- 页面联动：`test_tool_pages_ui_polish.py`
- 页面专项：对应 `test_*_ui_polish.py`

## 3.7 第 6 步：结果判定

按总规范里的 `PASS / SOFT FAIL / HARD FAIL` 输出结论。

## 4. 常用命令模板

## 4.1 帮助文案一致性

```powershell
pytest -p no:cacheprovider tests\test_ui_help_panel_texts.py -q
```

## 4.2 主要交互可用性

```powershell
pytest -p no:cacheprovider tests\test_ui_form_and_help_interactions.py -q
```

## 4.3 页面 UI 总套件

```powershell
pytest -p no:cacheprovider tests\test_tool_pages_ui_polish.py -q
```

## 4.4 典型页面专项

```powershell
pytest -p no:cacheprovider `
  tests\test_advanced_page_ui_polish.py `
  tests\test_crosshair_page_ui_polish.py `
  tests\test_magnifier_page.py `
  tests\test_about_music_ui_polish.py `
  tests\test_music_page_toolbar_state.py `
  -q
```

## 4.5 只查单个页面时

示例：

```powershell
pytest -p no:cacheprovider tests\test_tool_pages_ui_polish.py -k "flash_page" -q
```

## 6. 页面级执行最小清单

如果只是改了一个页面，至少完成下面这些动作：

### 6.1 文案改动页

- 跑帮助文案一致性测试
- 展开帮助面板抓 1 张图
- 核对路径、文件名、说明步骤

### 6.2 表单改动页

- 验证输入框可编辑
- 验证校验器没有把输入卡死
- 验证下拉有值
- 验证配置回写

### 6.3 布局改动页

- 抓 `1440 / 980` 两档
- 看横向滚动条
- 看按钮遮挡
- 看帮助展开后的首屏

### 6.4 状态联动改动页

- 触发至少 1 次状态变化
- 看 badge / summary / action bar 是否同步

## 7. 多页面改动时的执行顺序

如果本次不是单页面，而是同类页面一起改，建议按下面顺序查：

1. 先查公共组件
- 比如帮助面板、状态条、action bar、共享布局函数

2. 再查改动最大的页面
- 先抓主要风险点

3. 再查同类页面
- 看是否出现风格不统一、某一页漏改

4. 最后跑总套件
- 防止“局部页过了，全局回归挂了”

## 9. 失败后的标准动作

### 9.1 文案失败

- 修文案
- 重跑文案一致性测试
- 重抓帮助展开图

### 9.2 输入 / 选项失败

- 先定位是控件状态问题还是配置回写问题
- 修复后重跑交互测试
- 再看摘要和状态条是否同步

### 9.3 布局失败

- 缩小到具体宽度
- 修复后抓同一宽度前后对比图

### 9.4 污染真实环境

- 立刻停止当前测试或检查
- 清理临时目录
- 核对真实配置是否被改动
- 修正隔离方式后再继续

## 10. 最终定义

以后我每次说“这轮我已经检查过了”，默认含义就是：

- 我按总规范和本模板做过后台静默自查
- 不是只看代码
- 不是只跑一条测试
- 也不是只凭主观感觉

如果没有按这套模板完成检查，我就不应该对你说“都没问题”。
