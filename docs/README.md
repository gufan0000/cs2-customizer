# docs/ 导览

**先说结论：想修个 bug 或加个功能，这个目录你基本不用读。**
该读的是根目录的 [CONTRIBUTING.md](../CONTRIBUTING.md)。

这里放的是工程过程档案——历次专项的度量、问题清单、设计约束、结项报告。
它们对项目本身有用（避免同一个坑踩第二次），但对新来的人有两个门槛：
**全是中文**，而且**满篇内部编号**（`UP-072` 是 UI 性能专项的问题号、
`R9-A` 是回归轮次、`QA-001` 是非 UI 质量登记册的条目号）。

保留它们而不是删掉，是因为这些文档记录的是**判断过程**，不只是结论——
「为什么当初否掉了 A 方案」这种信息，代码里留不下来。

## 两个贯穿全部文档的方法论

这两条是项目反复吃过教训才立起来的，读任何一份档案前先知道它们，能省很多困惑：

**一、「全绿」之前先问分母。** 本项目已经三次栽在"某个维度全绿其实是根本没有判据、
或者少测了一整个轴"上：

- 排版审计跑了十一轮都只跑**完整模式**，一开紧凑模式立刻抓出三类真缺陷（`UP-100`）；
- 页面审计报告只写「页面 22」，读起来像全覆盖，实际分母是 27，两个真缺陷就藏在
  没被覆盖的 5 页里（`UP-096`）；
- 字号只测 1.0 / 1.25 两档，而某类缺陷只在走满三档时才显形（要连续两次重排才累积到位）。

所以文档里报结论时都会写清分母，看到"全绿"而没有分母的，先怀疑。

**二、判据必须验「回退即变红」。** 一条不该绿却绿了的判据，比没有判据更危险——
它让人以为这块有人看着。所以每条判据都要在
[`scripts/revert_verify.py`](../scripts/revert_verify.py) 里有一个断点：
把产品代码**真的改坏**，确认对应测试**真的变红**。

实测这道工序稳定逮出约三成"假绿"判据。判据的错法目前攒到五种，最常见的是
**量错了通道**——测的东西看起来对，但不是用户实际走的那条路径。
（最近一次：给 README 截图时首页显示「音频·需检查12」，查下去发现是截图脚本
跳过了后台的资源目录初始化，产品本身没问题。）
