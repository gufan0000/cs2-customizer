# 帆派助手 UI 第一阶段执行清单 v1

## 1. 阶段定位

第一阶段只做两件事：

- 收敛设计系统
- 精修全局框架

这一阶段的目标不是“做出新皮肤”，而是把当前 UI 的基础规则统一起来，让后续逐页打磨有稳定底座。

第一阶段结束后，应该达到的效果是：

- 左侧导航、顶部栏、卡片、按钮、输入框的视觉语言更一致
- 页面之间的层级和密度更稳定
- 主界面整体更成熟，但用户操作路径基本不变
- 不影响现有业务功能，不引入新的功能性风险


## 2. 严格范围

### 本阶段允许做的事

- 调整颜色 token
- 调整圆角、间距、字号等设计规格
- 调整导航栏、顶部栏、卡片、按钮、输入框的样式
- 调整少量全局布局节奏
- 调整页面通用容器和通用状态表达

### 本阶段禁止做的事

- 不改页面路由和页面 ID
- 不改导航结构和功能归属
- 不改业务逻辑和数据流
- 不改账号、更新、音频、准心、热键等功能逻辑
- 不做大面积页面重排
- 不同时混入新功能开发


## 3. 主要文件与职责

### 核心样式文件

- [theme_manager.py](../theme_manager.py)
  作用：主主题颜色与全局 QSS 生成
- `ui_modern_styles.py`（后续重构中已并入 `theme_manager.py`，仓库里不再有此文件）
  作用：在主题基础上的现代化增强样式
- [ui_design_system.py](../ui_design_system.py)
  作用：按钮、输入框、卡片、间距、圆角等规格定义
- [page_theme_helper.py](../page_theme_helper.py)
  作用：页面级通用样式应用和组件归类

### 全局框架文件

- [gui_widget.py](../gui_widget.py)
  作用：主窗口骨架、导航栏、顶部栏、内容容器、账号快捷入口

### 本阶段原则上不主动动的文件

- `pages/*.py`
  说明：除非某个通用样式调整后出现明显布局问题，否则不在第一阶段逐页精修


## 4. 执行顺序

### 步骤 A：设计 token 收敛

目标：

- 先把“规则”统一，再谈页面好看

重点文件：

- [ui_design_system.py](../ui_design_system.py)

具体动作：

- 统一按钮高度、按钮圆角、按钮 padding
- 统一输入框高度、边框宽度、圆角
- 统一卡片内边距、卡片圆角、卡片阴影
- 统一全局间距基线
- 检查现有 spec 与实际 QSS 是否有明显偏差

完成标准：

- 所有常用控件规格有明确单一标准
- 不再出现“设计系统定义一套，QSS 实际写另一套”的明显偏差


### 步骤 B：主题层级收敛

目标：

- 让颜色系统和文字层级更清楚

重点文件：

- [theme_manager.py](../theme_manager.py)

具体动作：

- 明确品牌色和状态色边界
- 拉开主文字、次文字、提示文字的层级
- 优化页面背景、卡片背景、悬浮背景、选中背景的对比关系
- 统一 `titleLabel`、`sectionTitle`、`hintLabel`、`valueLabel` 等通用角色

完成标准：

- 同类文本在不同页面看起来像同一系统
- 背景层级更清晰，但不花
- 状态色不会和品牌色冲突


### 步骤 C：现代增强样式减法重构

目标：

- 保留现代感，但减少“叠样式”的不稳定性

重点文件：

- `ui_modern_styles.py`（后续重构中已并入 `theme_manager.py`，仓库里不再有此文件）

具体动作：

- 检查与 `theme_manager.py` 的重复样式
- 合并重复定义，减少互相覆盖
- 精修导航选中态、主按钮渐变、卡片背景梯度
- 去掉视觉收益小、但维护成本高的样式细节

完成标准：

- 样式来源更清楚
- 不再出现一类控件在两个文件里强覆盖的混乱情况
- 现代感保留，但更克制、更稳定


### 步骤 D：全局框架精修

目标：

- 先把“壳”做稳

重点文件：

- [gui_widget.py](../gui_widget.py)

具体动作：

- 精修左侧导航的标题区、分组标题、选中态节奏
- 精修顶部栏的高度、基线、左右布局关系
- 精修右上角账号快捷按钮与模式切换按钮的视觉协调
- 检查完整模式与紧凑模式下顶部栏一致性
- 精修内容区顶部与卡片区的第一屏留白

完成标准：

- 左侧导航更像成熟桌面软件骨架
- 顶部栏更整洁，账号入口更自然
- 完整模式和紧凑模式视觉规则一致


### 步骤 E：页面通用容器校准

目标：

- 不逐页大改，但保证通用页面容器都在统一规则下

重点文件：

- [page_theme_helper.py](../page_theme_helper.py)

具体动作：

- 统一常见 objectName 的映射策略
- 明确哪些组件走全局主题，哪些页面允许局部自定义
- 确保页面根容器、标题、说明、按钮和卡片都能稳定命中通用样式

完成标准：

- 新页面和旧页面更容易共享统一视觉规范
- 后续第二阶段逐页打磨时成本更低


## 5. 第一阶段的明确交付物

第一阶段完成后，应交付这些结果：

- 一版收敛后的设计 token
- 一版更稳定的全局主题样式
- 一版更克制的现代增强样式
- 一版精修后的全局主框架
- 一份“第一阶段完成前后对照说明”
- 一份可运行的打包版本


## 6. 验收标准

### 视觉验收

- 左侧导航层级更清楚
- 顶部栏更整洁
- 主按钮、次按钮、输入框、卡片看起来来自同一套系统
- 页面第一屏不再显得松散或层级模糊

### 易用性验收

- 老用户无需重新学习路径
- 现有高频按钮仍在原有位置附近
- 状态信息更集中，不更难找
- 操作效率不下降

### 稳定性验收

- 不出现页面打不开
- 不出现按钮丢失、错位、遮挡
- 不影响账号登录、配置编辑、导航切换、音乐控制、更新机制
- 完整模式和紧凑模式都正常


## 7. 验证流程

每个子步骤完成后都做下面这些验证。

### 代码级验证

```powershell
python -m py_compile gui_widget.py theme_manager.py ui_design_system.py page_theme_helper.py
```

### 轻量运行验证

- 离屏实例化 `MainWindow`
- 检查顶部栏、导航栏、内容堆栈是否正常加载
- 切换一次页面，检查标题和选中态是否正常

### 人工界面验证

至少人工检查下面这些页面：

- 基础设置
- 账号中心
- 准心设置
- 音乐播放
- 关于软件

### 打包验证

- 打一个可运行的测试包
- 打开 exe 检查主界面、导航栏、顶部栏、账号入口


## 8. 风险控制规则

### 规则 1

- 每次只改一层，不把 token、框架、页面精修混成一个超大提交

### 规则 2

- 如果需要碰 `gui_widget.py`，优先只改样式和布局，不动页面装载逻辑

### 规则 3

- 如果某个样式调整会迫使多个页面改布局，先停下来拆小范围，不要硬推

### 规则 4

- 第一阶段不追求“惊艳”，只追求“统一、稳定、成熟”


## 9. 建议拆分成的实际实施批次

### 批次 1

- `ui_design_system.py`
- `theme_manager.py`

结果：

- 先把设计规范和主题基础打稳

### 批次 2

- `ui_modern_styles.py`

结果：

- 清理重复增强样式，降低后续维护成本

### 批次 3

- `gui_widget.py`

结果：

- 精修导航栏、顶部栏、内容区第一屏骨架

### 批次 4

- `page_theme_helper.py`
- 少量必要的通用页面兼容修正

结果：

- 保证页面层在统一框架下稳定运行

### 批次 5

- 打包
- 备份
- 形态复检


## 10. 第一阶段完成后的下一步

只有第一阶段完成并稳定后，才建议进入第二阶段逐页打磨。

第二阶段优先页建议是：

- 基础设置
- 账号中心
- 准心设置
- 音乐播放
- 关于软件

也就是说，第一阶段负责“骨架统一”，第二阶段才负责“重点页面变精致”。


## 11. 最终原则

第一阶段的成功标准不是：

- 变化最大
- 最炫
- 最像重做

而是：

- 改完之后，用户觉得更顺眼
- 用起来还是原来的节奏
- 没有引入功能问题
- 后续每个页面都更容易继续优化
