# CS2 Customizer 后台静默自查规范 v1

## 1. 文档定位

本文档是 `cfg-cs2customizer` 仓库内长期执行的交付规范。

目标只有一个：

- 把“做完后自查”从主观感觉，变成固定流程、固定证据、固定放行标准。

本文档只保留一层规范：

- `后台静默自查`
  - 适用于日常开发、页面打磨、文案修订、局部功能修复、发版前常规复查。
  - 必须满足“后台静默、绝不影响当前前台操作”。

这份规范刻意不包含虚拟机、隔离会话、黑盒环境之类的复杂流程。
后续默认都以“同会话后台静默自查”作为标准执行路径。

## 2. 适用范围

本文档适用于以下改动后的自查：

- UI 布局、样式、主题、页面结构调整
- 文案、帮助说明、提示语、状态文本修改
- 输入框、下拉框、复选框、滑块、按钮等交互控件修改
- 页面状态联动、配置回写、帮助面板展开/收起行为修改
- 音频、覆盖层、GSI、CFG、热键、导入导出等功能改动

本文档不适用于以下场景：

- 纯理论设计讨论，尚未进入仓库落地
- 与本桌面应用无关的官网、服务端、运营文档变更
- 单纯数据清洗、资源搬运但未影响程序行为的工作

## 3. 术语定义

### 3.1 静默

本规范中的“静默”是硬约束，不是“尽量不打扰”。

静默必须同时满足：

- 不抢当前桌面焦点
- 不弹前台窗口
- 不打开文件夹
- 不拉起外部浏览器
- 不播放真实音频
- 不注册或占用用户当前可感知的全局热键
- 不覆盖或污染用户真实配置
- 不写入用户真实 CS2 目录

### 3.2 放行

放行不是“我感觉差不多”，而是：

- 本规范要求的检查项已执行
- 结果已留痕
- 无阻断级问题
- 残余风险已明确记录

---

## 4. 核心原则

### 4.1 证据先于结论

任何“没问题”“已通过”“可交付”都必须有对应证据：

- 测试结果
- 截图产物
- 文案对齐检查
- 关键行为验证记录

### 4.2 先静态、再交互、再视觉

推荐顺序固定为：

1. 静态完整性
2. UI 合约检查
3. 交互联动检查
4. 离屏视觉审计
5. 改动相关专项测试

### 4.3 当前会话绝不做真实系统级骚扰测试

在用户当前会话里，不允许做下列行为：

- 真实全局热键验证
- 真实音频设备切换
- 真实文件夹弹出
- 真实驱动安装
- 真实覆盖层抢最前
- 真实桌面点击注入

这类行为不属于本规范；本规范只负责后台静默自查。

### 4.4 验收范围跟随改动升级，不跟随主观信心收缩

改动越大，自查范围只能变大，不能因为“我觉得问题不大”而缩小。

---

## 5. 覆盖边界

## 5.1 本规范必须覆盖的内容

- 标题、说明、状态区是否正确显示
- 问号帮助是否能展开，文案是否完整
- 输入框能否输入、校验是否正常
- 下拉选项是否存在、默认值是否合理
- 复选框 / 单选框 / 滑块 / 标签页切换是否有效
- 控件联动后的摘要、状态条、action bar 是否同步
- 页面在常见宽度下是否拥挤、裁切、横向滚动
- 改动页相关的自动测试是否通过
- 文案中的资源目录、CFG 文件、帮助说明是否与代码一致

## 5.2 本规范明确不负责的内容

- 真实游戏内热键触发
- 真实 VB-Cable 驱动安装与设备切换
- 真实桌面覆盖层最前显示
- 真实 GSI 网络链路
- 真实 CS2 目录写入后的即时游戏行为

如果以后确实需要验证这些内容，应单独列出“人工实机复核清单”，但不纳入本规范。

---

## 6. 进入条件

满足以下任一条件，就必须执行后台静默自查：

- 改了 `pages/` 下任意页面
- 改了 `widgets/` 下影响 UI 的公共组件
- 改了 `ui_help_panel.py`
- 改了状态条、摘要、action bar、表单行为
- 改了资源路径、帮助文案、配置回写逻辑
- 改了会影响页面显示或交互的配置逻辑

---

## 7. 环境隔离要求

后台静默自查必须运行在“静默模式”下。

## 7.1 图形环境

- 使用 `QT_QPA_PLATFORM=offscreen`
- 不允许使用真实桌面截图作为主检查手段
- 页面截图统一使用 `QWidget.grab()`

当前仓库现状：

- [tests/conftest.py](../tests/conftest.py) 已默认设置 `QT_QPA_PLATFORM=offscreen`

## 7.2 配置隔离

必须避免污染用户真实配置。

推荐做法：

- 单元 / 交互测试里使用 `monkeypatch + tmp_path`
- 由我手动发起的静默检查里，为测试子进程注入临时 `LOCALAPPDATA`
- 或临时改写 `get_app_data_dir()` / `get_config_dir()` 到测试目录

不得做的事：

- 直接读写用户当前 `%LOCALAPPDATA%\\CS2Customizer\\config.json`
- 直接写用户真实资源目录

## 7.3 副作用隔离

必须 stub 或 monkeypatch 以下行为：

- `os.startfile`
- `QFileDialog`
- `QMessageBox`
- `keyboard.add_hotkey / hook / unhook`
- 音频真实播放函数
- 驱动安装器
- 真实 GSI 服务连接
- 真实 CS2 CFG 写入

原则：

- 同会话只验证“调用意图”和“UI 状态变化”
- 不验证真实系统结果

## 8. 标准执行顺序

### 8.1 第一步：静态完整性检查

目标：在不启动真实交互前，先排除“路径、映射、文案、键名”这类低级错误。

必查项：

- 页面帮助 key 与 `PAGE_HELP_TEXTS` 是否一一对应
- 文案中的资源目录是否与代码真实扫描目录一致
- 文案中的 CFG / GSI 文件名是否与代码一致
- 关键页面配置键是否存在
- 关键枚举值是否与 UI 下拉项一致

当前可直接利用的仓库能力：

- [ui_help_panel.py](../ui_help_panel.py)
- [tests/test_ui_help_panel_texts.py](../tests/test_ui_help_panel_texts.py)

### 8.2 第二步：UI 合约检查

目标：确认页面骨架和控件状态本身是成立的。

每个被改页面至少检查：

- 页面标题存在且非空
- 页面 lead 文案存在且非空
- 状态卡存在
- 帮助按钮存在
- 帮助面板存在
- 关键输入框存在
- 关键下拉框存在且有选项
- 关键复选框 / 单选框存在
- 底部 action bar 存在
- 默认状态不出现空白摘要或明显无意义文本

推荐优先使用：

- [tests/test_tool_pages_ui_polish.py](../tests/test_tool_pages_ui_polish.py)
- 各页面专属 UI 测试文件

### 8.3 第三步：交互联动检查

目标：确认控件不是“摆着能看、点了没反应”。

每个被改页面至少覆盖 1 组真实交互：

- 输入框输入后，配置或摘要发生变化
- 下拉切换后，状态条或 dependent UI 发生变化
- 复选框 / 单选框切换后，联动区启用 / 禁用正确
- 滑块变化后，标签文本同步
- 标签页切换后，action bar 文案或按钮变化正确
- 帮助按钮点击后，帮助面板展开，且文字非空

当前仓库已具备的能力：

- [tests/test_ui_form_and_help_interactions.py](../tests/test_ui_form_and_help_interactions.py)
- [tests/test_tool_pages_ui_polish.py](../tests/test_tool_pages_ui_polish.py)

### 8.4 第四步：离屏视觉审计

目标：检查自动断言不容易发现的视觉问题。

必须离屏抓图，不准拉起真实桌面窗口。

推荐宽度档位：

- `1440`
- `1280`
- `980`

必要时增加：

- `1600`：宽屏大卡片页
- `900`：极限紧凑页

离屏审图必须关注：

- 是否出现横向滚动条
- 顶部状态区是否拥挤
- 主要按钮是否被遮挡
- 输入框是否过窄
- 帮助面板展开后是否挤坏首屏
- 文案是否明显截断
- 页面是否出现大片无意义空白

截图统一输出到：

- `artifacts/expert_audit_YYYYMMDD_batchNN/`

推荐命名：

- `<page>_<width>_default.png`
- `<page>_<width>_help_open.png`
- `<page>_<width>_after.png`

### 8.5 第五步：改动相关专项测试

除了 UI 层，还必须补跑与本次改动直接相关的逻辑测试。

示例：

- 文案改动：帮助文案一致性测试
- 表单回写改动：配置逻辑测试
- 资源路径改动：资源扫描与健康检查
- GSI 联动改动：GSI handler 测试
- 音频播放策略改动：音频策略与烟雾测试

原则：

- 不要求每次跑全仓库
- 但要求“改到哪，测到哪”

---

## 9. 阻断标准

以下任一项成立，后台静默自查直接判定失败：

- 帮助按钮不存在或打不开
- 页面关键输入框不可编辑
- 下拉为空或没有默认项
- 关键开关点击后无状态变化
- 页面出现明显裁切或横向滚动
- 配置写回逻辑失效
- 帮助文案中的路径与代码实际行为不一致
- 同会话自查污染了真实配置或真实资源目录

---

## 10. 结果分级

### `PASS`

- 所有规定项通过
- 无阻断问题
- 截图复核无异常

### `SOFT FAIL`

- 功能不受影响
- 但存在文案、视觉、可发现性、说明不一致问题

### `HARD FAIL`

- 输入、选择、切换、联动、帮助、布局、配置回写中任一关键路径失效

## 14. 标准执行配方

## 14.1 小型文案改动

适用：

- 帮助说明
- 按钮文本
- hint 文案
- 状态摘要文本

最低执行：

1. 帮助文案一致性测试
2. 被改页面的交互测试
3. 至少 1 张帮助展开截图

## 14.2 单页面 UI / 交互改动

最低执行：

1. 该页相关静态检查
2. 该页交互测试
3. 该页 `1440 / 980` 两档截图
4. `test_tool_pages_ui_polish.py` 对应专项

## 14.3 跨模块改动

最低执行：

1. 改动相关静态检查
2. 改动页面交互测试
3. 页面总套件
4. 逻辑专项测试
5. 至少 3 页离屏截图

## 14.4 发版前

必须执行：

1. 全量静态检查
2. 全量主要页面交互测试
3. 全量关键页面离屏截图
4. 相关逻辑专项测试
5. 输出最终静默自查结论

## 15. 执行主体与汇报模板

本规范默认执行主体是“我”，也就是助手在当前仓库内完成改动后，按这份规范主动做后台静默检查。

这意味着：

- 不是让你手动逐项点页面
- 也不是要求你自己维护一套复杂脚本
- 默认由我负责执行检查、整理证据、汇总结论
- 只有你明确要求时，才额外把某一步做成可复用脚本

每次自查后的输出建议固定为：

```markdown
本次覆盖
- 页面：
- 功能：
- 文案：

执行结果
- PASS / SOFT FAIL / HARD FAIL

已执行命令
- ...

产物
- artifacts/...

发现问题
- 无 / 列表

残余风险
- 无 / 列表
```

## 16. 失败处理规则

### 16.1 文案类失败

- 先改文案
- 再跑帮助文案测试
- 再抓帮助展开图复核

### 16.2 表单 / 交互类失败

- 先补最小失败用例
- 再修页面逻辑
- 再跑对应页专项

### 16.3 视觉类失败

- 先缩小到具体宽度与页面
- 修布局或文案长度
- 重抓同尺寸截图对比

### 16.4 副作用污染

- 立刻停止当前脚本或测试
- 清理临时目录
- 核对真实配置是否被改动
- 修正隔离方式后再继续

---

## 17. 关于工具化

当前标准不是“先做脚本再检查”，而是“由我按规范执行后台静默检查”。

后续只有在以下情况同时成立时，才考虑把其中一部分工具化：

- 某一类检查已经长期稳定重复
- 工具化不会改变检查结论的质量
- 工具化不会增加你维护成本

在此之前，本文档本身就是执行标准，我负责按它检查，而不是把检查责任转给脚本。

---

## 18. 最终定义

以后“做完了”不再等于“代码写完了”，而是必须同时满足：

- 改动已实现
- 本规范要求的后台静默自查已执行
- 证据已留存
- 无阻断问题
- 残余风险已透明说明

如果以上任一项不成立，就不应向用户宣称“没问题”或“可以交付”。
